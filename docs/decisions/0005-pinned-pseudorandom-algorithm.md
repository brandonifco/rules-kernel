# 0005 — A pinned, reference-verified pseudorandom algorithm

## Status

Accepted — 2026-09-13.

## Context

A predecessor engine's replay contract rested on `new Random(seed)` producing identical
output forever. Its frozen-transcript tests pin the exact narrated sequence of a scripted
fight, which is only meaningful if the generator is stable.

`System.Random`'s seeded behaviour has been stable in practice, and .NET 6 deliberately
preserved it when it changed the seedless path. But the stability is not contractual, the
documentation has never promised it, and it does not extend across runtimes or
reimplementations. Resting a replay contract on an undocumented implementation detail is a
risk that costs nothing to remove and is expensive to discover late: every stored seed in
the project silently means something different.

There is a second, subtler problem. Nothing about a sequence of values proves which
generator produced it. Two sources that agree today are still a compatibility break the
moment either is replaced, and without a recorded algorithm identity there is no way to
detect that from a stored replay.

## Decision

The randomness package provides **PCG32**, variant `pcg_setseq_64_xsh_rr_32`, as a
line-for-line port of the published reference implementation, so a reviewer can diff the
port against the C source rather than trust a paraphrase.

The port is pinned by reference vectors generated by *running* the reference
implementation, fetched at a pinned commit and hash-verified before compilation — not
transcribed from documentation or from anyone's memory. The leading vector uses the seed
pair the reference's own demo programs use, so it is checkable against a file this project
did not produce.

`RandomAlgorithmId` records which algorithm a sequence came from, and is part of replay
identity ([0003](0003-corpus-baselines-and-the-temporal-axis.md)). Replacing the generator
or adding a second one is a compatibility event, comparable as data rather than remembered
by a reviewer.

Bounded draws use rejection sampling rather than modulo. 2^32 is not a multiple of most
bounds, so a modulo mapping is not uniform. For small bounds the skew is around 2.3e-10 and
distorts nothing anyone will roll; rejection sampling is chosen on the stronger ground that
it is *exactly* uniform rather than uniform up to a discrepancy someone must argue is small
enough — and the skew is not small for large bounds, which a kernel cannot rule out.

No retry cap is imposed on the rejection loop. A source that never yields an accepted value
is a broken source, not a failed draw, and a cap would misreport the former as the latter.
Sources that cannot honour the distribution contract are expected to fail loudly:
`FixedSequenceRandomSource` throws on exhaustion rather than looping.

## Alternatives considered

**Keep `System.Random` with a recorded algorithm id.** Rejected: recording the identity of a
generator whose behaviour is not contractually stable records the wrong thing.

**Vendor the reference C implementation.** Rejected: it is third-party code, and
redistributing it buys nothing the derived vectors and a re-derivation recipe do not.

**Modulo with a documented bias bound.** Rejected; see above.

## Consequences

The vectors are the replay contract. Changing an existing value changes what every stored
seed means, and is a compatibility event requiring its own decision record — not a
regenerated fixture in an unrelated change.

Draw count is part of the observable deterministic contract, because rejection makes it
input-dependent. Tests assert it directly.
